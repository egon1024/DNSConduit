    Architecture and packet path

    This page describes how DNS Conduit accepts client queries, runs each query through a fixed pipeline on the dataplane, and returns a response. It is the mental model for transactions, pipeline phases, and tags. Configuration YAML, rule syntax, and observability setup live on their own pages — they are linked from this page where they touch the query path.

    Overview

    Conduit is a DNS forwarder: clients send queries to configured listeners; Conduit evaluates policy, picks an upstream pool and backend, forwards the query, and sends the upstream answer (or a generated error) back to the client.

    Conduit combines two runtime roles:

    RoleWhat it doesRequired?
    DataplaneServes DNS — listeners, per-query pipeline, upstream forwardingAlways (the conduit service)
    Control planeConfig apply, export, reload, gRPC, conduitctlOpt-in (control: block)

    When the dataplane answers a query, it uses the runtime snapshot in force at that moment — your effective config, rules, and forward settings as Conduit has already loaded and validated them. When you change configuration, Conduit validates the new settings and swaps them in for later queries; queries already in progress finish on the config they started with. If the new config fails validation, Conduit keeps the previous working snapshot and DNS keeps flowing. See Configuration model.

    SIGHUP (Unix) No Reload from disk — re-read startup file, clear overlay
    conduitctl reload Yes (at process start) Same as SIGHUP
    conduitctl apply Yes (at process start) Patch the in-memory overlay only

    End-to-end path

    From a client’s perspective, one DNS query through Conduit looks like this:

    1. The client sends a query to a configured listener address (UDP or TCP).
    2. Conduit opens a transaction at Receive and walks the pipeline in order — Parse, Request rules, Route, Forward, Wait for response, Response rules, and Send — until the query gets a DNS reply or is dropped (no reply).
    3. During Route, Conduit selects a pool and backend (see Pools and backends).
    4. During Forward and Wait for response, Conduit sends the query upstream and waits for an answer (or timeout) before Response rules run.
    5. During Send, Conduit returns the DNS response to the client. Drops at Parse or in Request rules / Response rules end the transaction with no reply.

  Listener->>Pipeline: start transaction
  Pipeline->>Pipeline: Parse
  Pipeline->>Rules: Request rules
  Rules-->>Pipeline: pool, tags, drop, …

  Pipeline->>Upstream: Forward query
  Upstream-->>Pipeline: DNS response
  Pipeline->>Rules: Response rules
  Rules-->>Pipeline: retry, drop, …
  Pipeline->>Listener: response or drop
  Listener->>Client: DNS response (if any)

    Conduit can record activity during the query path without slowing answers:

    • Metrics — counters and histograms at selected pipeline phases; series reference in Built-in metrics
    • Event export — dnstap and other sinks
    • Tracing — per-query pipeline trace when enabled

    Observation runs separately from the steps above. Busy or full sinks must not block DNS responses — see Concurrency and workers and the Observability pages.

    Transactions

    A transaction is everything Conduit remembers for one client query from Receive through Send. On one worker, it carries:

    • The question — queried name and type, plus client address, listener, and protocol (UDP or TCP)
    • Policy context — tags, selected pool and backend, and attempt history when retries occur
    • Messages — the query as received and, when available, the response Conduit returns to the client
    • Optional trace — pipeline trace when tracing is enabled for this query

    For logs and traces, each transaction has a unique internal id. The DNS message id in the packet (dns_id) is separate; Conduit preserves it on responses to the client.

    Transactions are not persisted across queries and are not exported as part of normal config — tags and per-query overrides are runtime-only.

    Pipeline phases

    Every query walks the same pipeline phases in order. Policy may drop the query (no DNS reply), jump ahead (for example straight to Send on failure), or loop back to Route for a retry when limits allow. With the full metrics profile, conduit_phase_duration_seconds records time in each phase.

    Default happy path (single attempt, no early drop):

    1. Receive
    2. Parse
    3. Request rules
    4. Route
    5. Forward
    6. Wait for response
    7. Response rules
    8. Send

    Response rules may send the pipeline back to Route (and then Forward again) when a retry is requested and attempt limits allow it — the pipeline is not a strict one-pass pipe.

    PhaseOperator-facing summary
    ReceiveListener accepts the DNS message (UDP or TCP) and opens a transaction on the worker.
    ParseValid single-question query only; malformed or unsupported shapes → silent drop (no DNS reply).
    Request rulesFirst-match request rules and request Rhai — set_pool, set_source_v4 / set_source_v6, tags, or drop; no match → default path to Route.
    RouteFirst attempt: selected_pool → default / first pool. Retry re-entry (attempt_count > 0): retry_pool (if set) → selected_pool → default. Sticky weighted backend on first attempt, exclude-tried on retries. Missing pool or exhausted pool → SERVFAIL → Send.
    ForwardSend upstream (UDP/TCP per forward.upstream_transport); forward.timeout_ms and source addresses apply. Hard errors → SERVFAIL → Send.
    Wait for responseWait for upstream answer or timeout; answer or timeout → Response rules (retry policy may follow).
    Response rulesFirst-match response rules and Rhai — accept, drop, or retry (retry / retry_now) → Route (Retries and transactions).
    SendReturn stored upstream wire or synthesize error (SERVFAIL common); UDP TC when truncated.

    Receive

    The listener accepts the client’s DNS message (UDP or TCP) and opens a transaction for it. Processing continues at Parse on the same worker that accepted the query.

    Parse

    Parse checks that the bytes are a valid DNS query with exactly one question, then records the query name, type, class, and (when present) the client’s EDNS UDP payload size for later replies.

    Conduit drops (no DNS reply) when the packet is:

    • Empty or not valid DNS on the wire
    • A DNS message that is not a query (for example a response)
    • A query with no question section
    • A query with more than one question

    From the client’s perspective a drop is silent — there is no answer and no synthesized error. Parse drops increment conduit_parse_rejected_total with a reason label (empty, wire_error, not_query, no_question, multi_question). Successful parses increment conduit_queries_total before Request rules run.

    Request rules

    Request rules run before Route. Conduit evaluates configured rules in first-match order: the first rule whose selectors match the query wins; later rules are skipped for that query.

    Built-in actions on a matching rule can, among other things:

    • set_pool — choose which pool Route uses on the first attempt
    • set_retry_pool — pool used on retry Route if retry occurs; first Route ignores it (request or response hook; does not trigger retry by itself)
    • set_tag — attach tags used by later selectors, export filters, or scripts
    • set_source_v4 / set_source_v6 — pin upstream egress for this query on every forward (request hook only). set_retry_source_v4 / set_retry_source_v6 — one-shot egress for the next retry forward only (request or response hook). See Source selection lifecycle.
    • drop / drop_now / clear_drop — soft or hard drop, or clear soft-drop intent (Rules and actions)
    • retry / retry_now / clear_retry / clear_retry_pool / set_retry_pool — retry family (Rules and actions)

    Actions on the matched rule run in list order — built-in steps and optional rhai scripts interleaved as written. Each rhai step runs at its position in the list. Scripts can refine pool choice, set tags, set retry_pool for a future retry on the request hook, or drop the query.

    When no rule matches, Conduit continues to Route with the default forward path. Rule syntax, hooks, and action reference: Rules and actions.

    Route

    Route picks the pool and backend for this attempt. Pool name resolution:

    1. First attempt (attempt_count == 0): selected_pool from request rules or default / first configured pool. retry_pool is ignored.
    2. Retry re-entry (attempt_count > 0): retry_pool if set (consumed), else selected_pool, else default / first pool.

    After each Route, Conduit updates selected_pool to the pool that attempt used. Multi-attempt behavior and when to re-stash retry_pool: Retries and transactions — Pool selection lifecycle.

    On the first attempt, Conduit selects a backend using sticky weighted choice among all members of the pool (see Pools and backends). On retries, Conduit picks among backends in the target pool that were not already used for that pool on this transaction — cross-pool retries only exclude backends tried in the target pool.

    Each forward attempt increments the transaction’s attempt counter. When the pipeline continues to Forward, conduit_queries_by_pool_total records the selected pool.

    If the pool name does not exist, the pool has no backends, every backend in the pool was already tried, or backend selection fails, Conduit sets SERVFAIL on the transaction and skips Forward — the query goes straight to Send.

    Forward

    Forward sends the query to the backend chosen at Route.

    Transport. Upstream traffic follows forward.upstream_transport (UDP only, TCP only, or UDP with TCP fallback when the UDP response has the TC (truncated) bit set). TCP clients can be configured to use upstream TCP as well (forward.client_tcp_uses_upstream_tcp).

    Timeouts. Each forward attempt is bounded by forward.timeout_ms (default 2000 ms). Socket read/write timeouts use the same value.

    Source addresses. Conduit binds outbound packets using global forward.sources_v4 / forward.sources_v6, optional per-pool sources_v4 / sources_v6, and any source overrides from rules or Rhai. IPv4 and IPv6 backends use the matching address family. See Dual-stack forwarding and Reference: forward.

    Immediate forward errors (for example send failure or too many outstanding queries to the same backend) set SERVFAIL and jump to Send. A successful send continues to Wait for response. Each failed attempt increments conduit_forward_errors_total. With the full metrics profile, each attempt also updates conduit_forward_attempts_total and conduit_forward_duration_seconds.

    Wait for response

    Wait for response is where the worker waits for the upstream answer after Forward has sent the query.

    • Answer received — the upstream wire is stored on the transaction (including response code) and processing continues to Response rules.
    • Timeout — no answer before forward.timeout_ms; conduit_forward_errors_total records reason="timeout" and processing still continues to Response rules so retry policy can run another attempt.
    • Hard forward failure — some errors skip waiting and go directly to Send with SERVFAIL (see Forward above).

    In current releases the wait runs on the same worker as Forward before Response rules; the separate pipeline step keeps tracing and diagrams aligned with the full path. Retry behavior after a timeout or error: Retries and transactions.

    Response rules

    Response rules run once an upstream wire is available or a forward timeout has occurred (still with no stored answer). Like Request rules, evaluation is first-match on the response hook, with optional Rhai scripts on the matched rule.

    Built-in actions can accept the upstream answer, drop the query (no built-in counter), request retry or retry_now (stay in or re-enter with the current pool), set set_retry_pool for a different pool on the next retry attempt, or adjust response metadata (for example set_rcode). Retry intent — from retry, retry_now, or Rhai — sends the transaction back to Route for another Forward attempt; conduit_retries_total increments for the target pool of that attempt.

    Global caps from orchestrator.max_attempts (default 3) and orchestrator.max_txn_duration_ms (default 5000 ms), plus pool exhaustion when no unused backend remains in the target pool, apply before each Route. When a limit is hit, Conduit sets SERVFAIL and moves to Send instead of forwarding again. Details and examples: Retries and transactions, Rules and actions.

    Send

    Send delivers the final DNS message to the client.

    If Forward stored an upstream answer on the transaction, Conduit returns that wire unchanged (subject to client protocol on the listener). If there is no stored answer — routing or forward failure, or retries exhausted — Conduit synthesizes a minimal error response using the transaction’s response code (commonly SERVFAIL, or a code set by policy). Synthesized responses echo the client’s question section and preserve EDNS when the query had it.

    On UDP, if the response would exceed the client’s EDNS payload size (or 512 bytes when EDNS is absent), Conduit truncates the message and sets the TC (truncated) bit so standards-compliant resolvers can retry over TCP.

    Successful replies and synthesized errors both complete the transaction on the listener; conduit_responses_total and event export run as configured (coarse rcode buckets on minimal, per-IANA rcode + ip_family on full). See Observability and Built-in metrics.

    Tags

    Tags are named runtime annotations on a transaction (boolean or string values in current releases). Request rules and Response rules — built-in actions and Rhai on those hooks — set tags; selectors on later rules test them.

    Tags persist across retries on the same transaction unless cleared. They are useful for:

    • Branching policy (selectors on tag presence or value)
    • Gating event export or tracing (tag_required, trace activation)
    • Correlating logs and metrics with policy decisions

    Tags are not part of the on-disk config file or normal config export. Script and API details: Rhai, Rules and actions.

    Retries and re-entry

    When Response rules request a retry, Conduit counts the attempt and re-enters at Route — in the current pool or using retry_pool from set_retry_pool when set. Retries avoid backends already used in the target pool on this transaction. Further attempts stop at orchestrator.max_attempts, orchestrator.max_txn_duration_ms, or when the target pool has no unused backends — typically yielding SERVFAIL. Retry transitions increment conduit_retries_total for the target pool.

    Runtime snapshot

    A runtime snapshot is the bundle of settings Conduit uses to answer queries at a given moment: effective config (listeners, pools, forward behavior), loaded rules and scripts, and observability filters. All listener workers share the same snapshot until you change configuration.

    When you reload or apply new settings, Conduit validates the change and builds a new snapshot for later queries. SIGHUP and conduitctl reload reload from disk; conduitctl apply updates the overlay through the control plane. Queries already in flight keep using the settings they started with — they do not jump mid-query to a half-applied config. conduit_config_generation reflects the active generation at scrape time.

    If validation fails, Conduit keeps the last-good snapshot (the previous working settings) and continues serving DNS.

    Some changes update the snapshot immediately but still need a process restart to take effect on the wire — for example listener bind addresses and forward egress sockets. Conduit logs when that applies; see Configuration model and Reload and export for reload, overlays, and what requires a restart.

    Concurrency and workers

    Current releases run the dataplane in a sync-style model: each ingress worker accepts a client query, runs the full pipeline on that OS thread — including blocking upstream wait at Forward — then sends the reply before taking the next query on that thread. There is no separate policy or upstream I/O worker pool today.

    sync here is descriptive shorthand for that behavior. It is not a YAML config value — there is no runtime selector in current releases.

    W[Ingress worker]
    W --> recv[recv]
    recv --> pipe[full pipeline + upstream wait]
    pipe --> send[reply]
  end

    Worker counts and limits

    Ingress concurrency is configured under listeners::

    • listeners.threads — worker threads per entry in listeners.listeners (use listeners.reuse_port: true on UDP when threads > 1). Total ingress workers = threads × number of listener entries. Field reference: Reference: listeners.
    • orchestrator.txn_table_capacity — capacity of the in-flight transaction table on the datapath (bounds how many queries the process tracks at once, independent of per-query retry count). Field reference: Reference: orchestrator.
    • forward.outstanding_per_backend — cap on concurrent upstream queries per backend address. Field reference: Reference: forward.

    Under load or slow upstreams, a busy ingress worker cannot accept another client query until the current transaction finishes (including upstream wait). Tune threads and reuse_port when you need more parallel ingress capacity.

    Alternative runtime models (not shipped)

    Designs that split ingress, policy, and upstream I/O into separate worker pools — so ingress does not block on upstream DNS wait — have been discussed internally but are not implemented, not configurable, and not committed to any release. Do not expect related config keys in YAML today.

    Query outcomes and worker occupancy

    Outcome Client sees Notes
    Drop No reply (silent) Malformed wire, policy drop
    Response DNS packet Upstream answer or synthesized error (e.g. SERVFAIL when routing/forward/retries fail)

    Under current builds, one ingress worker stays busy for the entire transaction, including upstream wait.

    Metrics, event export (dnstap), and similar observation are handled separately from the query path. If an export queue fills up, Conduit drops export events and increments conduit_events_queue_dropped_total rather than delaying DNS responses.

    For reload, in-flight queries, and validation failures, see Runtime snapshot.
